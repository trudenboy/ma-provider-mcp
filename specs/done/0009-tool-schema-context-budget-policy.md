## Problem Statement

The server exposes 70 tools across 10 namespaces. MCP best-practice guidance
flags any surface above ~30 tools as a candidate for the search/execute
pattern, because every tool schema a client lists is context the model pays
for. Two questions had no recorded answer, so they kept resurfacing in review:

1. Should `config`/`debug` move to a search/execute shape to shrink the
   surface?
2. Is the per-tool `outputSchema` (auto-generated by FastMCP from the
   `*Brief`/`*Dump`/`*Inspect` return dataclasses) worth its context cost, or
   should it be dropped?

Without measurements both questions invite repeated speculative refactors. This
spec records the measured budget and the resulting policy so the decisions are
falsifiable and durable.

## Solution Summary

This is primarily a **decision record** backed by measurement, plus one small,
**conditional** implementation lever. Measurements were taken at FastMCP 3.3.1
by building every sub-server and serialising each tool to its MCP wire shape
(name + description + inputSchema + outputSchema + annotations); schemas are
generated from code and are identical to the live instance. The policy:
**keep one-tool-per-action** (search/execute rejected for `config`/`debug`),
**do not pursue `$defs` dedup** (measured negligible), and expose an opt-in
`output_schema=None` path for the two gated admin namespaces (`config`,
`debug`) intended **only** for distribution to MCP hosts that lack tool-search
deferred loading. Default behaviour (Claude Code, which defers schema loading)
is unchanged.

### Measured budget (FastMCP 3.3.1, 70 tools)

| Scope | chars | ≈ tokens | outputSchema share |
|-------|------:|---------:|-------------------:|
| Whole server (all 70 tools) | 82,247 | ~20,560 | 39% (~8,020 tok) |
| `config` (14 tools) | 22,885 | ~5,720 | 58% (~3,360 tok) |
| `debug` (12 tools) | 14,447 | ~3,610 | 42% (~1,540 tok) |
| Hot namespaces (playback/volume/media/playlists/queue) | — | — | 14–31% |

Lever evaluation:

- **`$defs` dedup of output schemas — rejected.** Measured saving ~330 tokens
  (config only), 0 in debug/library. MCP tool schemas are self-contained;
  `$defs` are not shared across tools, so cross-tool repeats do not dedup and
  intra-schema repeats are rare.
- **Drop `outputSchema` — the only material lever** (~8,020 tok server-wide,
  ~4,900 tok concentrated in `config`+`debug`). Mechanism: `output_schema=None`
  on the tool decorator keeps the typed dataclass return (still JSON-serialised
  into the `content` text block) but omits the schema and `structuredContent`.
  Trade-off: `outputSchema` is not pure overhead — it signals the return shape
  to the model pre-call and enables structured client rendering.
- **search/execute for `config`/`debug` — rejected.** The action catalog is
  small and fixed (26); the large dimension (50 live config targets) is already
  a runtime parameter, not separate tools. The Directory read/write-split rule
  forbids a single `execute` tool, so the surface only collapses to ~6 tools,
  at the cost of losing typed schemas, forcing `params: dict[str, Any]`, and
  adding a discovery round-trip.

### Host behaviour (verified on the live instance)

- Claude Code uses **tool-search / deferred loading**: tools arrive deferred and
  schemas load on demand, so the full schema cost is **not** paid every turn.
  Hosts without tool-search (claude.ai connectors, OpenClaw, Hermes) pay it
  per turn.
- `outputSchema` works on the deployed host: schema-bearing tools
  (`config_list_targets`, `debug_list_providers`) return valid results. The
  reported upstream issues about `outputSchema` dropping tools / hiding results
  do not reproduce here.

## Acceptance Criteria

1. A documented policy states that the server **keeps one-tool-per-action** and
   that search/execute is rejected for `config`/`debug`, with the recorded
   reasons (small fixed catalog, read/write-split rule, typing loss).
2. The policy records that **`$defs` output-schema dedup is not pursued**, citing
   the measured ~330-token saving.
3. A repeatable measurement procedure exists (a test or script) that reports
   per-namespace schema byte/token totals and the `outputSchema` share, so the
   budget can be re-checked after tool changes.
4. If the `output_schema=None` lever is implemented, it is **opt-in** and scoped
   to `config`/`debug`, leaves hot namespaces untouched, and the typed dataclass
   return value is still delivered to the client as JSON text in `content`.
5. Toggling the lever does **not** change any tool's name, input schema,
   annotations, tags, permission gating, or runtime behaviour — only the
   presence of `outputSchema`/`structuredContent`.
6. Existing tests stay green; no tool loses its `title`/`readOnlyHint`/
   `destructiveHint` annotations.

## Test Plan

- **Budget measurement test** — build each sub-server with a mock `mass`,
  call `list_tools()`, serialise each tool to its wire shape, and assert the
  per-namespace totals are within an expected band (pins the budget and fails
  loudly if a future change balloons the surface). Reports the `outputSchema`
  share per namespace.
- **outputSchema-toggle unit test** (only if the lever is implemented) — build
  the `config`/`debug` servers with the lever on; assert every tool has
  `output_schema is None`, yet a representative tool call still returns the
  dataclass payload as parseable JSON in the text content block. With the lever
  off, assert `output_schema` is present (default unchanged).
- **Annotation-invariance test** — assert all 70 tools retain `title` plus the
  applicable read/destructive hint regardless of the lever.
- **Manual verification** — exercise `config`/`debug` tools against the live
  instance with the lever on and confirm results remain readable and correct.
